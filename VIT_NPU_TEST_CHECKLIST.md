# ViT NPU functional test checklist

This checklist covers functional verification of the ViT NPU before adding a
real bus, AXI, DMA, or external-memory interface.

## 1. Correct description of the current architecture

The current functional simulation is:

```text
test_1 ... test_12/*.hex
    |
    v
SystemVerilog testbench
    - file loader
    - A/B/optional-bias memory models
    - batch/head-aware row/column gather and feeder
    - output collector and hex writer
    |
    v
NPU core
    - runtime batched-GEMM controller FSM
    - M/N/K-tail masks and bias enable
    - generic batch index (attention-head index in Phase C)
    - 2x2 output-stationary PE array
    - 4 tree PEs
      * 16 FP32 multipliers/PE
      * balanced 15-adder tree/PE
      * one local accumulator/PE
      * final bias add
    |
    v
npu_output_f32.hex
    |
    v
Python comparison against golden output
```

Important correction: the current NPU core does **not** contain two explicit
input and weight buffers. `a_memory`, `b_memory`, `bias_memory`, and
`output_memory` are testbench memory models. The testbench currently acts as
the memory subsystem and supplies packed vectors directly to the NPU core.

The current array is also not a classic systolic array yet. A and B values are
broadcast to PE rows and columns; values do not move from PE to PE every clock.
The precise name is a **2x2 output-stationary array with 16-lane vector/tree
PEs**. It can evolve into a systolic dataflow later, but calling the current
implementation a conventional systolic array would be misleading.

The controller is not a separate RTL module yet. Its
`IDLE/CLEAR/COMPUTE/BIAS/WRITE/DONE` FSM is part of
`vit_gemm_tree_array.sv`. The older `vit_q_tree_array.sv` remains only as the
known Q-only baseline.

The generic controller produces `batch_index`, `token_base`, `output_base`, and
`k_base`. The testbench uses those indices to gather A and B vectors. There is
no bus or physical SRAM interface yet, which is acceptable for the current
functional verification phase. The custom functional handshake is
`data_request/data_valid` on input and `result_valid/result_ready` on output.
Result data plus batch/token/output metadata stay in the WRITE state while the
consumer applies backpressure.

## 3. Global pass criteria for every test

Every test package should contain:

```text
01_input_A_f32.hex
02_weight_B_f32.hex       for model weights, or
02_input_B_f32.hex        for activation operands such as K-transpose/V
03_bias_f32.hex           when the operation uses bias
04_golden_output_f32.hex
npu_output_f32.hex        generated by ModelSim
manifest.json             shape, layout, counts, tolerance
```

For every result, check:

- [ ] Output word count is exactly correct.
- [ ] Output layout matches the documented row-major coordinates.
- [ ] Invalid M/N PE lanes are masked and skipped by the testbench collector.
  The current DUT emits a masked tile; it has no memory-write port yet.
- [ ] `done` is asserted once and only after the final valid result.
- [ ] No unexpected NaN or infinity appears.
- [ ] Report bit mismatches separately from numerical mismatches.
- [ ] Report maximum and mean absolute error.
- [ ] Report maximum relative error.
- [ ] Report the first mismatch coordinate.
- [ ] Report the largest-error coordinate and both values.
- [ ] Numerical comparison passes the tolerance chosen for that operation.

## 4. Phase A — harden the existing arithmetic and controller

- [ ] Test positive/negative normal values.

- [ ] Test round-to-nearest-even boundary cases.
- [ ] Confirm and document the current flush-to-zero subnormal policy.

Architecture change:

- NPU core: no structural change required.
- PE: no change unless a numerical bug is found.
- Controller: no change.
- Buffer/testbench: add small unit-level arithmetic testbenches only.

### A02 — small GEMM boundary, handshake, reset, and restart test

- [ ] Use a small matrix with odd M and odd N.
- [ ] Insert random gaps in `data_valid`.
- [ ] Verify that `k_base` advances only on accepted data.
- [ ] Verify accumulator clear between output tiles.
- [ ] Verify that bias is added exactly once.
- [ ] Reset while idle and while a calculation is active.
- [ ] Run two GEMMs consecutively and verify no accumulator/controller state
  leaks into the second run.
- [ ] Verify `start`, `busy`, and `done`, including exactly one completion per
  accepted start.

Architecture change:

- NPU core: no planned datapath change.
- Controller: fix only if stall or boundary behavior fails.
- Buffer/testbench: replace `data_valid=data_request` with a controllable
  latency/stall memory model.
- Output interface: `result_ready` is implemented in the generic core; run the
  stall regression before marking its hold behavior verified.

## 9. Buffer evolution plan

### Current stage

```text
Legacy B/C benches: file arrays provide A/B/bias/output behavior
Phase-E reference top:
  logical INPUT array for prepared patch-A
  reusable PARAM MAIN/AUX staging window
  fixed 0x1E6000-word SCRATCH address space
  four local GEMM PE accumulators
  no physical SRAM banking, bus, DMA, or external-memory timing model
```

The Phase-E arrays make address lifetime and in-place reuse executable, but
they are simulation/bring-up memories. They must not be counted as inferred
production SRAM without synthesis and banking analysis.

### After generic GEMM functionality is proven

Add simple functional memories inside or immediately beside the NPU core:

```text
A/activation buffer
B/weight buffer
bias buffer
C/output buffer or output FIFO
```

These can use direct testbench load/write ports. A bus is not necessary yet.
Calling the architecture a “two-buffer NPU” would omit bias and output storage,
so the more accurate description is two main operand buffers plus bias/output
storage.

For one active 2x2, 16-lane chunk, the minimum tile staging capacity is:

```text
A tile buffer: 2 rows x 16 lanes = 32 FP32 words
B tile buffer: 2 cols x 16 lanes = 32 FP32 words
bias staging:  2 columns          =  2 FP32 words
output staging: 2 rows x 2 cols   =  4 FP32 words
```

Two A banks and two B banks may later be used as ping-pong buffers to overlap
load and compute. That is a performance optimization, not a prerequisite for
functional correctness.

### During attention integration

Logical storage is required for:

```text
Q, K, V                     each [12,197,64]
attention scores            [12,197,197]
attention probabilities     [12,197,197]
attention head outputs      [12,197,64]
```

For functional ModelSim verification these can remain memory models. A future
hardware implementation should tile or stream them instead of assuming every
full tensor fits in on-chip SRAM.

### During full-layer integration

Logical storage is also required for:

```text
hidden-state ping buffer     [197,768]
hidden-state pong buffer     [197,768]
residual source              [197,768]
FC1 intermediate             [197,3072]
```

Ping-pong hidden-state buffers are useful for layer-to-layer execution.
Double-buffering weights or activations is a throughput optimization, not a
functional requirement, and should be added only after the non-overlapped
version passes.
